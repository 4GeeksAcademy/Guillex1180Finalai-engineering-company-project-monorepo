# Auditoría de serialización de la API TrackFlow

Fecha: 2026-11-23  
Alcance: todas las operaciones de `services/api/main.py` y routers incluidos. No se implementan rutas hipotéticas de recuperación de contraseña.

## Criterio y resultado

La superficie contiene 23 operaciones de router y dos operaciones de liveness (`GET /` y `GET /health`). Antes de esta auditoría, 20 de las 23 rutas de router declaraban `response_model`; faltaba un contrato para el análisis de incidencias y el CSV no declaraba su tipo de contenido en OpenAPI. `DELETE /users/{user_id}` ya respondía 204 sin cuerpo, pero no explicitaba `response_model=None`. El root era una respuesta de middleware fuera de OpenAPI. Se reemplazó por una ruta tipada y documentada que conserva la respuesta `{ "status": "ok" }`.

Resultado tras la implementación: **las 25 operaciones están cubiertas por un contrato de respuesta explícito**. Las 23 rutas de router declaran un `response_model`; los dos probes usan `StatusResponse`. El CSV declara `response_model=None` porque no es JSON y describe su respuesta `text/csv`; el DELETE declara `response_model=None` porque devuelve 204 sin cuerpo. No se retorna ORM crudo: SQLModel se proyecta en esquemas Pydantic y TinyDB se filtra con esquemas de salida.

## Fase 1 — Revisión inicial de autenticación

Se revisaron primero las rutas de identidad porque manejan credenciales, tokens y datos personales. En esta API no hay ORM de usuario: las credenciales y perfiles viven en TinyDB. Los servicios internos usan registros que contienen `hashed_password`, pero las respuestas pasan por modelos de salida Pydantic; el hash nunca forma parte de esos contratos. La contraseña se acepta solo como dato de entrada en registro/cambio de credenciales y se guarda hasheada.

## Comportamiento actual de respuesta por endpoint

Por tanto, un `dict` de TinyDB con un `response_model` adecuado sí queda filtrado/validado por FastAPI y no equivale a una respuesta dict sin tipar. No se encontró ningún handler que devuelva una entidad ORM cruda como respuesta.

La clasificación evalúa el contrato HTTP efectivo y su adecuación al consumidor. `DELETE` declara intencionalmente respuesta vacía (204), y la exportación CSV declara una `Response` no JSON y su contenido `text/csv` en OpenAPI; para ambos, `response_model=None` es la excepción correcta, no una respuesta sin serializar. Las respuestas de error generadas por `HTTPException` conservan el envelope estándar de FastAPI (`detail`) y no cambian la clasificación de la respuesta exitosa.

## Reglas de entrada y seguridad

- Se conserva el principio de esquemas de entrada independientes de los de salida. Modelos de escritura y proyecciones de respuesta aplicables usan `extra="forbid"` (incluye SKU, movimientos, usuarios, perfiles, auth y proveedores).
- El UUID de usuario en movimientos no se acepta del cliente: el handler lo asigna desde el usuario autenticado. Se retiró el campo de los tipos de petición del backoffice y se eliminó la dependencia del UUID local almacenado en navegador para autorizar la escritura.
- Las respuestas de movimiento de escritura conservan `sku_id` y `user_uuid` como identificadores relacionados: la confirmación no necesita los objetos relacionados completos y la atribución de auditoría del historial muestra explícitamente el identificador de operador. No se devuelve un objeto SKU anidado en los recibos de escritura.
- En `GET /inventory/orders`, la relación con SKU se representa como proyección plana (`sku_name`, `sku_code`), campos que consume la tabla del historial; se omite `sku_id` y no se anida el SKU completo. Se conserva `user_uuid` como identificador de auditoría mostrado por la UI, no se serializa el objeto de usuario.
- En `GET /auth/me`, la relación perfil sí es necesaria para la vista de cuenta: se devuelve una proyección anidada limitada a `id`, `name`, `phone`, `address`, excluyendo su FK `user_id`. Los endpoints `/profiles/me` devuelven esa misma proyección sin usuario anidado. El email y rol de `/auth/me` describen al llamante autenticado.
- Las listas de productos usan `SKURead` (incluye el stock calculado requerido por formularios, sin relaciones); la lista de usuarios usa `UserRead` para gestión administrativa; proveedores usan `SupplierResponse`, que expone los campos del directorio y no datos internos TinyDB. Incidencias devuelve solo agregados y no filas originales/PII.
- `/auth/login` devuelve un `access_token` bearer porque es la credencial que el cliente necesita para autenticarse; no devuelve un token interno adicional, email, contraseña ni hash.
- Las excepciones HTTP (401/403/404/409/422) conservan el envelope estándar FastAPI `detail`; las respuestas exitosas quedan explícitas.
- No hay endpoints de forgot/reset-password en esta API; no se crean rutas inventadas.

## Verificación

La verificación de Fase 3 se ejecutó después de los cambios de esquemas:

- Suite backend completa: **32 pruebas pasaron**, incluidos 4 subtests; se emitió una advertencia deprecada de Starlette/httpx, sin fallos.
- `cd uis/application && npm run typecheck`: completado correctamente (`tsc --noEmit`).
- Smoke HTTP local: `GET /health` y `GET /login` respondieron **200**.
- Comprobación aislada por HTTP con `TestClient`: `/docs` y `/openapi.json` respondieron **200**; OpenAPI contiene **25 operaciones** y los contratos representativos apuntan a los esquemas esperados (`StatusResponse`, `RegistrationResponse`, `AccessTokenResponse`, `StockOrderRead`). Se comprobaron respuestas reales de health, registro, login, `/auth/me`, creación de SKU, recepción inbound e historial; los shapes coinciden con los contratos y la atribución del movimiento coincide con el usuario autenticado.
- En los ejemplos de registro y login no se devuelve email, contraseña ni hash; `/auth/me` devuelve el email del usuario autenticado y el perfil limitado sin `user_id`. El historial usa `sku_name`/`sku_code` planos y no incluye `sku_id` ni un objeto SKU anidado.

La prueba HTTP de rutas representativas se ejecutó directamente con `TestClient` y bases temporales aisladas, no pulsando “Try it out” desde un navegador en Swagger UI. Por ello se verificaron la disponibilidad de `/docs`, los contratos publicados y los shapes HTTP; la interacción manual del navegador con Swagger queda pendiente si la evaluación exige específicamente esa acción visual. El inventario actual clasifica las **25 operaciones como ✅**; los casos `204` y CSV son respuestas especiales explícitas (`response_model=None`), documentadas en OpenAPI, no excepciones ocultas.
